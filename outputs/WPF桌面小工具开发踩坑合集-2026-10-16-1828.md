# WPF 桌面小工具开发踩坑合集

> 来源：快捷启动面板（WPF/.NET 8 + Win32 互操作 + Everything 集成）两天的真机开发实录。每条 = 现象 → 根因 → 修法。凡标「实测」的都是真机验证过的判据，不是文档转述。适用于：给 Windows 写任何托盘常驻 / 全局热键 / 带图标网格的自用小工具。

## 一、坐标与 DPI

### 1. Win32 工作区返回物理像素，WPF Left/Top 是 DIP

- 现象：150% 缩放屏上，按 Win32 工作区计算的面板位置整体偏右下 50%，且位置记忆把错值固化。
- 根因：`MonitorFromPoint`/`GetMonitorInfo` 全是物理像素；WPF 坐标是设备无关像素（DIP），150% 时 1 DIP = 1.5 物理像素。
- 修法：`GetDpiForMonitor(hMonitor, MDT_EFFECTIVE_DPI)` **按屏**取 DPI（多屏缩放比可不同），物理矩形 ÷ (dpi/96) 换算成 DIP 再赋给 Left/Top。
- 判据：留一条 posCheck 自检日志（窗口物理矩形 vs 工作区物理矩形），一跑就能看出偏没偏。

### 2. 「我的屏没开缩放测不出来」是多 DPI 盲区

- 教训：涉及坐标互转的功能，交付前要么问用户缩放比例，要么直接用自检日志数值验证，不能只在自己屏幕上目测。

## 二、窗口激活与失焦隐藏

### 3. Activate() 会被前台锁静默拒绝

- 现象：面板弹出后"点外面不消失"，且完全无报错。
- 根因：Windows 前台锁（防抢焦点）会静默拒绝 SetForegroundWindow；窗口从未激活 → 永远不产生 Deactivated → 失焦隐藏逻辑永不触发。
- 修法（四层，实测有效）：
  1. EnsureForeground：先模拟按下再松开 ALT（keybd_event）解前台锁，再 SetForegroundWindow；
  2. 显式验证：`GetForegroundWindow() == hwnd` 写进自检日志，不默认成功；
  3. 400ms 可见性巡检兜底：可见但未激活且无抑制理由 → 隐藏；
  4. 始终提供可见的 ✕ 关闭按钮——"没有可见退出入口"这类问题会反复出现。

### 4. 失焦隐藏必须有抑制器，否则杀死自己的功能流程

- 现象：右键菜单弹出、对话框打开、拖文件进来的瞬间面板消失，添加流程全废。
- 修法：失焦隐藏前查实际状态而不是计数器——菜单 IsOpen / 对话框计数 / 拖拽进行中（带 10s 到期防卡死）/ 编辑模式，命中则不隐藏。

## 三、WPF 布局与控件行为

### 5. 容器对齐属性不一定被模板消费

- 现象：HorizontalContentAlignment/VerticalContentAlignment 设在 ScrollViewer 上不生效。
- 根因：ScrollViewer 的模板是 ScrollContentPresenter，不消费这两个属性（≠ContentControl 的行为）。
- 修法：对齐设在**内容元素本身**（如内部 StackPanel/自绘 Panel 的 VerticalAlignment）。
- 教训：WPF 里"容器对齐属性是否生效"取决于模板实现，改对齐优先改内容元素。

### 6. 内置面板做不了布局语义时，自定义 Panel 成本极低

- 案例：要"末行不满时整行水平居中"，UniformGrid 永远末行靠左。
- 修法：自写 `class XPanel : Panel`，只需 override MeasureOverride/ArrangeOverride 两个方法（几十行），比找 workaround 快。

### 7. ContextMenu 是可继承属性，事件中赋值 = 时序竞争

- 现象：右键偶发弹出**窗口级**菜单而不是行菜单，间歇性复现。
- 根因：ContextMenu 沿视觉树继承，ContextMenuOpening 事件里赋值与 ContextMenuService 的解析存在竞争。
- 修法：弃用事件赋值，改 `PreviewMouseRightButtonUp` 显式命中行 → 构建菜单 → `Placement=MousePoint` 手动打开，行为确定。
- 泛化：WPF 可继承属性 + 事件中赋值 = 竞争温床，菜单类交互一律"显式命中 + 手动打开"。

### 8. OLE 拖拽：DragOver.Effects 必须是 DoDragDrop 所述效果的子集

- 现象：DoDragDrop 声明 Move，DragOver 写死返回 Copy → OLE 压成 None → Drop 事件**静默**永不触发。
- 修法：DragOver 按数据格式分别返回 Move/Copy；拖拽功能上线前必须真机拖一次（编译通过≠能拖）。

### 9. Hidden ≠ Close：视觉树持有的引用 GC 收不走

- 现象：面板隐藏后内存不回落（104.9MB > 验收线），越用越涨。
- 根因：窗口只是 Hide()，上次搜索结果行连着图标留在视觉树里，全部可达 → GC 合法地不回收。
- 修法：隐藏时清结果集（ItemsSource=null + 列表 Clear + 回磁贴视图），位图变垃圾后才轮到 GC。

## 四、内存治理

### 10. GC.Optimized 会"判断不值得收"而直接跳过

- 现象：GC.Collect(2, Optimized) 跑了，私有内存纹丝不动。
- 修法（实测有效组合，放后台线程）：
  ```csharp
  GCSettings.LargeObjectHeapCompactionMode = GCLargeObjectHeapCompactionMode.CompactOnce;
  GC.Collect(2, GCCollectionMode.Forced, true);
  GC.WaitForPendingFinalizers();
  GC.Collect(2, GCCollectionMode.Forced, true);
  ```
- 边界认知（实测数据）：托管回收 ≠ 私有内存回落。WPF 首次显示窗口时初始化渲染栈（D3D 设备/着色器/字形缓存），**一次性常驻 +25MB**，窗口隐藏不释放——这是 WPF 固有，不是泄漏。判别泄漏的方法是**同实例多轮压测**：几轮"使用→隐藏"循环后内存平直 = 有界健康；单调爬升 = 真泄漏。

## 五、事件与生命周期

### 11. 重建持有事件源的对象后，事件订阅必须随重建迁移

- 现象：切换热键后新旧热键全失灵，日志却显示"注册成功"。
- 根因：Dispose 旧 HotkeyManager 后 new 了新实例，但 Pressed 事件订阅还挂在旧对象上——新热键注册成功却无人响应。
- 修法：抽一个统一注册方法（销毁→新建→注册→**在同一处接事件**→记日志），所有调用方都走它；禁止两处分别接线。

### 12. 超时比实测最大耗时短 + 静默取消 = 故障不可见

- 案例：查询实测最坏 3.2s，超时设 4s 贴脸，超时后静默砍掉，用户只看到"没结果"。
- 修法：超时放宽到实测最坏的 2 倍以上；取消/超时必须记日志。

## 六、第三方集成（Everything 案例，可泛化）

### 13. 进程外 CLI 的固定开销，换进程内 SDK 即消失

- 实测：es.exe 每次调用固定 ~600ms（进程创建+IPC 握手，与结果量无关）；官方 Everything SDK（Everything64.dll + P/Invoke）单查询 **80–115ms**，提速 7–15 倍。
- 泛化：凡是"装了 A 软件想借它的索引/能力"，先查官方 SDK——DLL 直连通常比 CLI 包装快一个数量级。失败自动降级 CLI 兜底，可用性不受影响。

### 14. IPC 是否可并发，先测再上并发

- 实测：Everything 1.4 的 WM_COPYDATA 在其 UI 线程串行处理，两个客户端并行查询 = 排队翻倍（600ms → 1.5–3.2s）。
- 修法：改两阶段**串行**（高优先级查询先发先上屏）；SDK 层加 lock 串行化。

### 15. 「文档说支持」≠「本机链路可用」

- 案例：es.exe 文档支持多词/过滤语法，本机实测多词查询全灭、`ext:` 单独可用组合全灭——两次想当然的方案被真机推翻。
- 修法：过滤类/语法类功能先写 5 行探针在真机验证，再写正式代码。

### 16. 依赖"数据分布假设"的排序方案天然脆弱

- 案例：假设"垃圾文件夹不会刷满结果窗口"，被真实环境（同名备份文件夹家族）击穿。
- 修法：用户给出明确优先级时（程序>文件>文件夹），按优先级**全链路显式排序**，不打数据分布的补丁。

## 七、交付方法论

### 17. 交互功能必须真机走完整流程再交付

- 同一类事故撞了多次：添加流程被失焦隐藏杀死、拖拽从未生效、编辑模式没接拖拽处理器而文案承诺了可拖。
- 原则：**"代码能编译" ≠ "能用"**；每个交互路径（含失败路径）真机走一遍才算完成；提示文案是契约，承诺了就必须真实现。

### 18. 自检日志先行

- 本项目排查速度的底气全在 posCheck 式自检日志（DPI/位置/激活态/首帧耗时/分阶段耗时）。坐标、激活、耗时这类"看不见的状态"，写代码时就埋好数值日志，出问题一眼定位。

## 八、2026-10-16 晚补记（设置窗自动关闭引出的两个连环坑）

### 19. 对"关闭中"的窗口再调 Close 会抛异常，且托盘应用必须挂全局异常网

- 现象：设置窗失活自动关闭后，快速窗口切换时整进程静默消失（用户以为"卡死"）。
- 根因：Deactivated → Close() 进入关闭流程后，又一条 WM_ACTIVATE 再次触发 Deactivated → 对关闭中窗口再次 Close() → WPF 抛 InvalidOperationException（VerifyNotClosing）→ 无全局异常处理 → 进程终止。
- 修法：`_closing` 状态守卫（自动关闭路径置位 + Closing 事件兜底置位，覆盖手动关闭）+ try/catch；**应用启动第一件事挂 DispatcherUnhandledException（记日志吞掉保活）+ AppDomain/TaskScheduler 兜底（留法医记录）**——托盘常驻应用死一次，用户就丢一次工具，且没有日志无从取证。

### 20. WPF 的 IsActive 会因"关窗激活接力"卡死，真前台要用 GetForegroundWindow

- 现象：设置窗关闭后，点哪里面板都不隐藏；巡检显示 active=True，而系统前台明明是别的进程。
- 根因：同应用窗口关闭时 WPF 做"激活接力"把另一个窗口标记 Activated，但它并未真正成为 Win32 前台——此后永远收不到 WM_ACTIVATE DEACTIVATE，IsActive 永久卡 true，一切基于 WPF 激活态的逻辑全部失效。
- 修法：兜底巡检用 **Win32 真前台判定**（`GetForegroundWindow() == 窗口 hwnd`）而不是 WPF IsActive；WPF 事件照常保留处理正常消息流。泛化：**凡是依赖 WPF 窗口激活态做自动行为的，兜底判定一律查系统真前台**。
- 附：复现手法——SetCursorPos + mouse_event 驱动真实鼠标点击 + 2s 状态快照日志，比纯推理快得多。
